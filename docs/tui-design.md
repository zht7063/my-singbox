# My sing-box TUI 设计方案

- 状态：首版核心流程已实现；本文保留原始设计目标，实际功能和验证边界见 [TUI 使用指南](tui.md)。独立认证探针、已有部署修改端口及真实 VPS 验收仍待后续。
- 日期：2026-11-03。
- 设计基线：当前 TypeScript 3.0.0 CLI；现有 `init`、`doctor`、`isp-outbound` 及两节点路由模型。
- 目标用户：通过 SSH 在 Debian / Ubuntu VPS 上部署和维护 sing-box 的用户。
- 配套原型：[TUI 原型页](tui-prototype.html)。页面中的检测结果、地址、路径与任务进度均为演示数据，不读取本机、不执行命令。

## 1. 设计结论

增加显式入口 `my-singbox tui`，提供“状态首页 + 首次部署向导 + ISP 配置表单”。沿用现有 CLI，TUI 与 CLI 共享应用服务、校验器和配置生成器。

首版重点解决三件事：

1. 用户在一个表单中确认服务器地址和两个协议的端口；提交前能看到输入错误、占用信息和实际文件变更。
2. ISP 地址、用户名、密码、可选出口 IP 可以回看和编辑；测试结果清楚区分 TCP 可连接、SOCKS5 认证成功和出口 IP 检测成功。
3. 依赖检测逐项显示状态、原因和处理建议；完成操作后能分清文件已保存、容器已运行、本地检查已通过和外网尚未验证。

首版支持新部署选择端口、现有部署查看端口，以及已有 ISP 的添加、更新和移除。**已有部署修改监听端口放到后续阶段**：该操作涉及客户端重新导入、现有手改配置保留、多文件变更和服务恢复，不能复用当前拒绝覆盖的生成命令直接实现。

## 2. 现状及设计约束

| 现状 | 代码依据 | 对设计的影响 |
| --- | --- | --- |
| `init` 先 doctor，再补齐缺失文件并启动；保留已有文件 | `src/cli/init.ts:12` | 新部署与已有部署分流，不能把向导当成覆盖已有配置的入口 |
| `doctor` 已有结构化的 `Check` 类型，但由 `runDoctor` 组装并输出文本 | `src/doctor/checks.ts:3`、`:107` | 提取检查集合供 TUI 消费；不解析带颜色或格式的 CLI 输出 |
| Node >= 22，Linux/glibc >= 2.28，x64/arm64；产品声明只支持 Debian/Ubuntu | `package.json:6`、`src/doctor/checks.ts:17`、`README_CN.md:7` | 增加发行版识别；macOS 开发机可预览 UI，但不能宣称可部署 |
| 端口为模型常量 8388 / 8443，`.env` 不接受端口键 | `src/model.ts:50`、`src/core/env.ts:15` | 增加端口模型和序列化支持，缺省值保持兼容 |
| 服务端模板验证要求模板端口与模型端口相等 | `src/core/render-config.ts:39` | 先验证模板原型，再把用户端口写入最终入站；不能仅修改模型 |
| Clash 渲染器已经从模型取端口 | `src/core/render-clash.ts:42` | 确保服务端和客户端使用同一个已校验模型 |
| TCP 检查读取配置端口，UDP 检查写死 8388 | `src/core/start.ts:84`、`:129` | 改为按入站协议生成 TCP/UDP 检查计划 |
| Compose 使用宿主机网络 | `compose.yaml:7` | 端口写入 sing-box 入站，无需添加 Docker `ports:` 映射 |
| 服务端 ISP 路由独立于客户端，不增加监听端口和客户端节点 | `README_CN.md:57` | ISP 表单不展示“ISP 节点端口”；操作预览不包含 `clash.yaml` |
| CLI 输入通过 readline/stty，命令逻辑已支持注入依赖 | `src/cli/main.ts:7`、`src/cli/commands.ts:13` | TUI 单独管理终端，复用业务依赖，不能嵌套两套输入系统 |
| 构建产物必须仅依赖 Node 内置模块，禁止 npm 运行时 dependencies | `tools/check-bundle.mjs:15` | TUI 库作为构建依赖整体打包，保留零外部运行时依赖 |
| 凭据文件权限为 0600，生成器拒绝覆盖已有文件 | `src/core/env.ts:152`、`src/cli/gen-config.ts:17` | 表单编辑只改内存，提交才落盘；涉及已有文件必须有独立变更计划 |

特别注意：当前 doctor 找到旧 `docker-compose` 时会给 WARN，但 `startNode` 实际要求 `docker compose`。TUI 对部署操作必须把缺少 Compose v2 视为阻塞，不能显示“可以继续部署”。应在共享检查逻辑中消除这项不一致。

## 3. 范围和入口

### 3.1 命令设计

```text
my-singbox tui                 # 在当前部署目录打开 TUI
my-singbox tui --help          # 显示终端要求和用途
```

不传子命令继续显示现有帮助；现有 `init`、`doctor`、`isp-outbound` 的文本交互和管道用法保持兼容。首版不自动把已有命令切换成全屏界面。

TUI 检查 stdin/stdout 是否都是 TTY、终端是否支持交互（例如 `TERM=dumb`），以及宽高是否足够。不满足条件时明确退出，给出现有 CLI 命令；**不能自动回退到会写配置或启动服务的 `init`**。普通 CLI 输出继续适合重定向和自动化。

首版中文界面，文案通过独立消息表组织；字段名、协议名、路径和命令保持原样，方便未来增加英文。

### 3.2 功能边界

| 能力 | 首版 | 后续 |
| --- | --- | --- |
| 依赖、部署文件和容器状态查看 | 支持 | 诊断报告导出 |
| 首次部署：服务器地址、SS/VLESS 端口、可选 ISP | 支持 | 更多协议 |
| 已有部署端口 | 查看和诊断 | 增量修改、客户端迁移 |
| ISP 添加、更新、移除 | 支持 | 路由规则编辑器、多 ISP |
| SOCKS5 连通性及出口检测 | 支持，用户主动触发 | 持续监测 |
| 启动和按需重新检查 | 支持 | 停止、卸载、镜像升级 |
| 配置导出 | 显示本地 `clash.yaml` 路径及导入说明 | 订阅服务、二维码 |
| 安装依赖和开放防火墙 | 显示建议，用户自行操作 | 不纳入当前设计 |

## 4. 信息架构和导航

```text
状态首页
├─ 新部署向导（仅空部署目录）
│  ├─ 运行条件
│  ├─ 服务器地址与端口
│  ├─ ISP（可跳过）
│  ├─ 变更预览
│  └─ 执行与结果
├─ 运行条件与诊断
├─ 端口与服务器信息（已有部署只读）
├─ ISP 配置
│  ├─ 添加 / 更新
│  ├─ 主动测试
│  └─ 移除预览
└─ 启动与检查 / 客户端导入说明
```

首页由事实驱动推荐动作：

- **空目录**：还未部署，推荐“开始部署”。本地 OS、Node、架构可立即读取；Docker 等外部检查显示“未检查”，进入向导后执行。
- **已有完整配置，容器运行**：推荐“查看运行状态”；ISP 仍允许维护。完整配置不等于健康，服务状态必须有独立时间戳。
- **已有配置，容器未运行**：显示“配置已存在，服务未运行”，可选择启动并检查。
- **文件缺失或配置不一致**：显示缺失/不一致详情；新部署向导禁用，提供备份和手动修复指引。不能从残缺文件推断安全的重建方案。
- **已有其他/旧版部署**：标识“需要核对”，列出现有入站和客户端节点数量；首版不静默迁移。现有 CLI 支持的旧 ISP 迁移要经过单独预览与确认后才可从 TUI 进入。

页面状态包含当前位置、当前部署目录、正在编辑的草稿和检查时间。切页不写文件；取消整项操作清空该操作的凭据草稿。

## 5. 界面原型

以下为宽屏示意。中文按终端显示单元计算宽度，实际组件不能用 JavaScript 字符串长度画边框。地址均为文档保留地址，仅用于演示。

### 5.1 状态首页：把下一步放在最前面

```text

│ 状态   运行条件   端口信息   ISP   客户端                 │
├─────────────────────────────────────────────────────────┤
│ 当前部署：未初始化                                      │
│ 推荐操作：确认运行条件，然后填写服务器地址与端口。        │
│                                                         │
│ > [ 开始部署 ]       [ 检查运行条件 ]                    │
│                                                         │
│ 本地环境     Linux · arm64 · Node 22                     │
│ Docker       未检查                                     │
│ 部署文件     未创建                                     │
│ ISP 出口     未配置；默认出口 direct                     │
│                                                         │
│ 提示：ISP 只控制 VPS 出口，共用两个基础监听端口。          │
```

首页不提供 CPU、内存图表或大量滚动日志。首版主要服务配置和排错，避免把配置工具做成监控平台。

### 5.2 运行条件：给出原因和可执行的下一步

```text
┌ 首次部署 · 1/5 运行条件 ─────────────────────────────────┐
│ 状态      检查项                  检测结果               │

│ [FAIL]  > Docker Compose          缺少 v2 插件            │
│ [OK]      Docker daemon           可以访问               │
│ [WARN]    ss / iproute2            未安装                 │
│ [OK]      部署目录                可写                   │
│                                                         │
│ Docker Compose                                          │
│ 需要 docker compose v2 插件，当前环境无法启动部署。       │
│ 请先按 Docker 官方安装指引安装，再返回重新检查。         │
│                                                         │
│ [ 重新检查 ]   [ 查看处理建议 ]   [ 继续：不可用 ]        │
```

检查进行中用 `[检查中]`；尚未运行用 `[未检查]`；未执行的后续项用 `[跳过]`，不伪装成 OK。FAIL 阻止依赖该能力的动作，但用户仍能查看诊断和退出。

```text
┌ 首次部署 · 2/5 服务器与端口 ─────────────────────────────┐
│ 服务器公网 IP / 域名                                    │
│ > [ 203.0.113.10                              ]          │
│   自动检测候选，允许修改；此处为演示地址。                │
│                                                         │

│ VLESS / REALITY   [ 8443  ]  TCP                          │
│                                                         │
│ 8388/tcp    [未发现占用]   本机监听表，检查于 14:32:08     │
│ 8388/udp    [未发现占用]   本机监听表，检查于 14:32:08     │
│ 8443/tcp    [冲突]         已有其他监听，详情权限不足      │
│                                                         │
│ ! VLESS 端口已被占用，请修改后重新检查。                  │
│ [ 检查端口 ]   [ 为冲突字段建议端口 ]                    │
│                                                         │
│ 防火墙与云安全组尚未验证，部署后需自行放行。              │
│ [ 上一步 ]                          [ 下一步：不可用 ]  │
```

输入过程中只做本地格式验证；失焦或停顿后提示错误。监听检查由按钮明确触发，避免每个按键都调用外部进程。修改任一端口会立即让此前的检查结果失效。

### 5.4 ISP 表单：编辑字段与真实认证测试分开

```text
┌ ISP 出口 · 更新配置 ─────────────────────────────────────┐
│ 启用 ISP SOCKS5   [ 是 ]                                 │
│ 代理主机 IP      [ 198.51.100.20                     ]   │
│ 代理端口         [ 1080                              ]   │
│ 用户名           [ 修改用户名… ]  当前值已保存           │
│ 密码             [ 更换密码…   ]  当前值已保存           │
│ 期望出口 IP      [ 留空使用代理入口 IP               ]   │
│                                                         │
│ 路由：保留当前服务端规则；默认出口以当前配置为准。        │
│ 不新增端口；本次不修改 clash.yaml。                      │
│                                                         │
│ [ 测试代理 ]    状态：未测试                             │
│ 测试会连接该代理，并通过代理请求出口 IP 查询服务。        │
│ 添加 / 更新需测试通过；修改字段后需重新测试。            │
│                                                         │
│ [ 取消 ]                              [ 预览变更 ]      │
└─────────────────────────────────────────────────────────┘
```

添加场景用户名和密码为空、均为必填。更新场景使用“保留已有 / 修改”的显式状态，密码输入框不回填星号占位值；用户不能误把 `********` 保存成新密码。凭据默认隐藏；按需展开只对当前字段有效，失焦或 10 秒后隐藏。

“期望出口 IP”用于验证代理出口：留空时要求检测结果等于代理入口 IP，入口与出口不同时须填写真实出口。更新场景提供“保留当前期望值 / 修改 / 重置为入口 IP”三个显式动作；更换入口时提示确认旧期望值。不能把它当作只读备注、路由绕过规则或指定出口的设置。

## 6. 输入和交互规则

### 6.1 通用键盘与布局

| 按键 | 行为 |
| --- | --- |
| Tab / Shift+Tab | 下一个 / 上一个可用控件 |
| ↑ / ↓ | 列表和菜单内移动；输入框内遵循编辑器行为 |
| Enter | 激活当前按钮；表单输入框内移动到下一字段，不直接提交部署 |
| Space | 切换复选框、单选项 |
| Esc | 关闭帮助 / 弹层；无弹层时返回上一级，脏草稿需确认丢弃 |
| Ctrl+C | 编辑阶段退出；有草稿先确认；提交阶段请求在安全点停止 |
| ? | 非输入框焦点时打开当前页帮助；输入框内正常输入问号 |

不使用 Tab 切换顶层标签，避免与表单焦点冲突。顶部标签也是可聚焦控件；不依赖鼠标。页脚随焦点提供简短提示。

宽度 >=100 列时可展示列表和右侧详情；80–99 列采用单列；60–79 列采用逐字段紧凑向导；低于 60 列或 18 行显示调整终端大小的提示，只保留退出/恢复。resize 保留内存草稿，不截断输入值。使用真实显示宽度处理中文、组合字符和粘贴；ASCII 状态文字是颜色之外的冗余编码。`NO_COLOR` 禁色、`TERM=dumb` 拒绝全屏模式，ASCII 边框模式不改变文字内容。

### 6.2 服务器地址与端口校验

- 地址默认提供公网 IP 检测候选，用户确认后使用。允许合法 IPv4、IPv6 和域名；主机字段不带 URL scheme、路径、端口。文档保留地址只用于原型，实际部署应提示其用途。
- 公网 IP 检测失败仍可手动输入；检测过程可以取消。DNS 解析失败显示独立的警告，不把域名格式合法显示成“已验证可达”。
- 端口必须是十进制整数 1–65535；首版两个基础入站不能使用同一端口，因为都需要 TCP。SS 必须检查 TCP 和 UDP；VLESS 检查 TCP。
- 默认 8388 和 8443，保留一键恢复默认。1–1023 不是格式错误；说明低端口的实际权限取决于容器权限和系统设置，最终由启动结果决定。
- “建议端口”只为用户指定的冲突字段，从可配置高位候选区间选择并检测，展示建议，接受后才修改。检查范围仅限本机，不做外部扫描。
- 优先用 `ss` 的数值监听结果覆盖 IPv4/IPv6、通配地址和协议；看到监听但看不到进程时仍是冲突，不能判定可用。
- 无 `ss` 时可用临时 TCP/UDP 独占绑定补充检查，但绑定测试不是最终保证；检查 IPv4/IPv6，释放 socket，禁止复用选项。权限不足或检测失败返回“未知”，用户可在预览中明确选择继续。
- 不可把监听表中属于自己当前 sing-box 的端口标红为其他程序冲突。只读已有部署页显示“由当前服务使用”；无法确认归属时显示“已监听，归属未知”。
- 提交前重新检测占用。即使刚通过也存在竞争窗口，启动失败仍需按真实错误处理。禁止自动终止进程或自动更改已确认的端口。

### 6.3 ISP 字段与测试

首版与现有核心能力一致：代理主机只接受 IPv4 或严格 IPv6；分开输入主机和端口，组装 `.env` 时 IPv6 写成 `[IPv6]:port`。不在 UI 宣称支持现有 `parseIspAddr` 不支持的域名、SOCKS URL 或匿名认证。

用户名和密码均要求 UTF-8 1–255 字节、无控制字符和非法 Unicode；用户名不能含冒号。密码不 trim，允许现有规则接受的空格、反斜线、引号、美元符号。由 `envQuote` 序列化，禁止拼 shell 命令。粘贴多行产生字段错误，不拆成多个命令或多个表单动作。

更新时显式保留已有凭据；修改后又清空会报必填错误。“保留”是状态，不是空字符串的特殊含义。当前默认值来自 `.env`，须与 `config.json` 比较；二者不一致先显示差异和来源，让用户确认期望状态，不能称为“保留当前运行值”。测试结果绑定整个代理草稿指纹；修改地址或凭据后失效，且不能在错误信息或日志中输出指纹输入。

测试分层显示：

| 级别 | 能说明什么 | 不能说明什么 |
| --- | --- | --- |
| TCP 连接 | 目标地址和端口接受连接 | 服务一定是 SOCKS5、凭据正确 |
| SOCKS5 协商和认证 | 协议及当前用户名/密码可用 | 所有目标网站可达 |
| 经代理 HTTPS 查询出口 IP | 当前测试请求的实际出口 | 服务端已有域名规则都已生效 |

现有 `IspService.socksEgressIp` 使用 curl，通过 `socks5h` 请求 HTTPS 出口查询服务，最多尝试四个服务，每次 15 秒；不是纯 TCP 探测，也不是整个测试只需 15 秒。首版复用该路径，在 diagnostics 中增加“ISP 测试依赖 curl”的条件检查；凭据继续通过 stdin 配置传给 curl，不放入 argv。新增轻量 TCP / SOCKS5 握手探测用于阶段详情，最终结论仍需完整出口校验，不能从 TCP 成功推断认证成功。

建议进一步让连接超时 5 秒、整个测试预算 15 秒，作为共享服务的显式改动验证，不静默改变现有 CLI 重试策略。所有探测可取消。发起前列出出口查询服务和用途，不后台测试；HTTPS 请求通过代理隧道，凭据不发给查询服务，查询目标由代理端解析。结果只保留测试时间、阶段和脱敏错误。出口 IP 按地址语义比较，避免 IPv6 不同缩写误报；这是对当前字符串比较的修正。检测出口与期望不同时，显示两者，用户确认修改期望后重新测试。可以先看预览，但添加/更新的最终提交必须通过当前草稿的出口校验，维持现有 CLI 的要求。

添加 ISP 时展示模板中的实际路由条件；更新时展示并保留已有条件，不能用模板默认域名覆盖用户路由。移除或旧配置迁移的引用范围以核心生成的计划为准。暂不提供规则编辑器。

## 7. 运行条件与部署状态模型

把检查分为两组，页面中分别呈现：

- **运行条件**：Node、发行版/glibc、架构、Docker CLI、Compose v2、daemon 访问、部署目录可写、可选 `ss`；启用 ISP 时增加必需的 curl。
- **部署状态**：文件是否存在和可解析、客户端与服务端基础端口是否一致、镜像版本、容器归属与状态、最近一次配置检查和监听结果。

`doctor` 的 `OK/WARN/FAIL` 是检查结论；UI 加入 `idle/running/skipped/unknown` 作为执行状态。没有执行的项不参与“全部通过”。检查返回结构化修复建议和所影响的能力，而不是只有一段英文字符串。

优先使用 `docker info` 的实际连接结果判断 daemon 能否访问；本地 socket 文件访问权限只是辅助信息。遵循 Docker 当前 context 和 `DOCKER_HOST`，不能因为没有 `/var/run/docker.sock` 就误判远程 Docker 可用性；但本项目 host 网络和本地绑定挂载要求部署目标与本机一致，**首版远程 context 应标记不支持部署**，避免把本地路径交给远程 daemon。当前 socket 检查的行为属于需要修正的前置问题。

建议数据形状（提案，不代表现有 API）：

```ts
type CheckState = 'idle' | 'running' | 'done' | 'skipped' | 'unknown';
type Capability = 'deploy' | 'start' | 'edit-isp' | 'inspect-udp';
interface DiagnosticResult {
  id: string;
  state: CheckState;
  status?: 'OK' | 'WARN' | 'FAIL';
  summary: string;
  detail?: string;
  checkedAt?: string;
  blocks: Capability[];
  remediation?: { text: string; command?: string }[];
}
```

依赖检查可有限并行，固定 UI 顺序，限制并发与超时。Docker CLI 不存在时依赖它的检查标记跳过并指向根因。用户从外部安装依赖后手动重新检查；不在 TUI 内执行 sudo、curl 安装脚本或 apt。

## 8. 应用服务与状态机

### 8.1 分层

```text
现有 CLI ─┐
          ├─ 应用服务：读取状态 → 校验草稿 → 计划 → 应用 → 验证
新 TUI ───┘                  │
                             ├─ 核心：模型、渲染、ISP、env、redact
                             └─ 适配器：文件、Docker、监听探测、SOCKS5 测试
```

先提取应用服务，再接 TUI。TUI 不通过伪造 stdin 驱动 `init` 或 ISP 菜单，不抓取人类日志猜测状态；CLI 文本和 TUI 阶段显示由同一组事件分别渲染。

建议目录：

```text
src/
  app/
    deployment.ts       # 部署清单、首次部署计划及执行
    diagnostics.ts      # 检查集合与能力阻塞
    isp.ts              # 对现有 ISP service 的交互无关适配
    operations.ts       # 操作事件、恢复结果与取消
  core/
    ports.ts            # 字段校验、入站检查计划
  adapters/
    port-probe.ts       # ss / bind 适配器
    socks-probe.ts      # SOCKS5 认证与 HTTPS 出口查询
  tui/
    main.tsx
    screens/            # home, diagnostics, setup, isp, review, result
    components/         # 字段、检查列表、步骤栏、脱敏日志
    state/              # 纯 reducer、草稿和页面状态机
    messages/zh-CN.ts
```

代码布局是建议；简单操作不必为了目录层次包装一层无业务含义的服务。

### 8.2 草稿到计划

```ts
interface DeploymentDraft {
  serverAddress: string;
  ports: { ss: number; vless: number };
  isp?: { host: string; port: number; user: string; pass: string; egressIp?: string };
}
interface OperationPlan {
  id: string;
  kind: 'initial-deploy' | 'isp-add' | 'isp-update' | 'isp-remove' | 'start';
  files: { path: string; action: 'create' | 'update'; sensitive: boolean }[];
  serviceAction: 'start' | 'restart' | 'none';
  requiresClientReimport: boolean;
  // 同时绑定草稿版本和所有参与规划的文件/模板指纹。
  baseRevision: string;
}
```

秘密只放在应用层的内存操作上下文；预览 DTO 不含原始密码，事件不携带原始文件内容。上面的草稿类型不能直接用于日志、遥测或持久化。首版没有遥测和凭据草稿自动保存。

```text
loading → editing → validating → review → applying → verifying → result
              ↑           │       │          │            │
              └─ 错误返回 ─┘       └─ 返回修改┘            └─ 失败 → recovery → result
```

返回修改会使计划失效；确认时重新检查草稿版本、文件/模板指纹和运行条件。文件被外部编辑时拒绝应用旧计划，要求刷新预览。写操作获得部署目录独占锁；并发 TUI/CLI 操作也应使用同一锁，不能只锁 UI 按钮。

`AbortSignal` 传至适配器。编辑和检查阶段立即取消；提交阶段在明确安全点退出，显示正在完成的写入/恢复。退出码建议：成功或提交前正常退出 0，失败/部分完成 1，输入或终端不支持 2，用户中断 130；最终退出码不能被“返回首页后退出”重置掉未处理的失败状态。

## 9. 文件变更、恢复与中断

### 9.1 首次部署

适用条件是目标四个部署文件均不存在；可以有不相关文件。存在任何部署文件都先进入已有部署诊断，不自动套用新部署计划。

确认前完成草稿校验和预览；确认后加锁、重新验证基线，生成凭据和候选文件，在私有暂存目录验证候选配置，最后用排他写入提交。不得在用户确认前写凭据或启动容器。Docker 候选配置校验可能拉取固定版本镜像，应在计划中说明。

`writeFileAtomic` 只保证单文件原子替换，四个文件不能被称为一次原子事务。维护 0600 的操作恢复记录，记录阶段、目标、原状态与候选摘要，不记录凭据正文；候选文件和含秘密备份同样为 0600，目录为 0700。未完成记录要在下次 TUI 启动时可见。

文件发布前失败可清理本次独有的暂存文件。发布后失败默认保留已生成配置，显示每个文件与容器的实际状态，可选择“按当前配置重新启动并检查”；不重新生成密钥，不自动删除用户可能已经取走的客户端配置。记录与文件不一致时转入手动诊断。

### 9.2 ISP 更新/移除

从 `src/cli/isp-outbound.ts` 的私有 `apply` / `rollback` 编排中抽取共享用例，复用 `IspService` 及现有文件原语；目前没有独立导出的完整事务 API。保留备份、候选校验、文件恢复和重启语义，应用层增加可展示的结构化结果。只管理 `.env`、`config.json`，不把 `clash.yaml` 纳入备份或事务。新增部署内的 ISP 一次性写进初始模型，避免先启动再执行一轮 ISP 更新。

现有 CLI 在 config 变化时先校验候选并询问重启，拒绝即不安装；仅 env 变化时不重启但仍检查健康；完全无变化的添加可能为了修复健康状态再次请求重启，无变化的移除则不检查健康。TUI 的计划与结果必须表达这些分支，不把返回 0 一律显示为“服务已验证”。首版不新增“保存但不应用”分支。

预览提示重建会中断连接。现有 `IspService.recreate` 没有限定服务名，可能重建 Compose 项目中的其他服务；TUI 接入前应将共享服务动作限定到 `sing-box` 并验证自定义 Compose 兼容性，或准确列出全部受影响服务，不能只写“重启 sing-box”掩盖作用范围。

文件恢复和服务恢复分别上报。进程被 SIGKILL 或 SSH 断开不能依赖内存 `finally` 保证恢复，下一次启动需要根据操作记录检测未完成状态。首版先提供可靠检测、检查和恢复指引；自动跨进程恢复须单独验证，不能凭最近一个备份文件自动覆盖。

### 9.3 敏感输出与终端恢复

复用并扩展 `secretValues/redact`，注册旧值、草稿新值和新生成值，统一处理 stdout、stderr、错误详情、预览与日志尾部。处理子进程分块输出时要跨块脱敏，避免半个密码从相邻块漏出。外部输出中的 ANSI 控制序列必须过滤，不能让容器日志控制全屏终端。

所有正常退出、异常和可处理信号都执行终端恢复：raw mode、光标、替代屏幕、挂起的输入监听。SIGKILL 无法执行恢复，帮助中给出终端失常时的 `reset` 指引；不承诺所有中断都能自动恢复。

## 10. 自定义端口的贯通设计

新增可选 `.env` 键 `SS_PORT`、`VLESS_PORT`。缺失时使用 8388/8443；键存在但为空或非法必须报错，不能悄悄回退。

变更清单：

1. `ENV_KEYS`、环境解析/生成和 `.env.template` 支持新键。
2. `buildModel` 从环境构造端口，`SS_PORT/VLESS_PORT` 常量继续作为默认值，避免破坏已有导出。
3. 服务端渲染器先按既有规则验证模板原型 tag/type/默认端口，再从模型应用用户端口。不要为了可配置端口去掉原型完整性校验。
4. 新部署的 `config.json` 和 `clash.yaml` 从同一模型生成，预览、文件、检查和防火墙说明共享同一监听计划。
5. 启动 UDP 检查按实际 Shadowsocks 入站及端口执行；不再以端口是否等于 8388 决定协议。
6. doctor 通用权限指引不再硬编码默认防火墙端口；未知配置时明确说默认值，已知配置时从计划/文件生成。
7. 不在 host 网络 Compose 中添加重复的端口映射。

已有部署事实以当前 `config.json` 和 `clash.yaml` 为准，`.env` 只是生成输入。发现端口不同则显示不一致，不自动“同步”。后续修改端口需要增量修改两个配置中已知节点、保留无关 YAML/JSON、备份三份文件，并明确要求用户重新导入客户端。

## 11. 技术选型与发布

推荐先做一个窄范围 **Ink + React** 技术验证，通过后用于 TUI。它适合 TypeScript、多页表单和随异步结果更新的列表；组件边界与 reducer 有利于测试。选择仍需以实际构建和 SSH 表现验证，本文不声称已验证某个版本兼容。

| 方案 | 优点 | 代价 / 决策 |
| --- | --- | --- |
| Ink + React | 状态驱动，表单/列表组织清楚，适合现有 TS | 增加 bundle 与许可证维护；首选，需验证整体打包 |
| 逐题 prompts | 首次向导很轻量 | 多字段回看、状态首页和重绘较弱；适合简化降级，不作为完整 TUI |
| 自写 ANSI 全屏引擎 | 可控制体积 | 输入法、宽字符、焦点和 resize 维护成本高；不建议首版采用 |

保持 `package.json` 的 `dependencies` 为空；选定的 UI 库放入构建依赖并由 esbuild 内联，发布包不依赖额外安装。不要直接引入要求 Bun 或原生编译的渲染引擎。

首轮按现有方式把 TUI 打入 `dist/cli.js`；只在收到 `tui` 命令时挂载 UI、初始化 raw mode，普通 CLI 和 `dist/index.js` 导入不得产生终端副作用。若体积或启动成本不可接受，再引入独立 `dist/tui.js`；该方式需要先修改目前拒绝所有相对运行时导入的 bundle 检查，不能直接加动态导入后声称兼容。

验证关注：Node 22/24，ESM 打包、React reconciler 的内联依赖、JSX 编译配置、无外部包导入、许可证扫描和 notices。记录构建前后的 CLI 体积、普通命令冷启动与 TUI 首屏时间，基于实际测量决定是否拆包。首版不顺便修改支持的系统矩阵。

## 12. 分阶段实施

| 阶段 | 交付 | 完成条件 |
| --- | --- | --- |
| P0：基础接口与技术验证 | 结构化 diagnostics/事件；最小 Ink 页；打包实验 | 普通 CLI 无终端副作用，bundle/pack/license 检查通过，SSH 宽字符与 resize 可用 |
| P1：端口数据贯通 | 可选端口 env、模型/模板/客户端/启动检查一致 | 默认端口兼容；自定义 SS UDP 检查通过；已有配置不被覆盖 |
| P2：可用首版 | 首页、完整首次部署向导、ISP 表单/测试、预览/执行/恢复状态 | 可以完成一次新部署和一次 ISP 维护；失败状态准确 |
| P3：已有部署端口修改 | 增量补丁、备份恢复、客户端迁移说明 | 保留自定义配置；客户端与服务端一致；故障恢复验证通过 |

P0/P1 是可落地的前置项，不建议先用 TUI 包裹现有命令输出再补业务接口。复杂度主要在端口一致性、进程中断和恢复，而非边框绘制。

## 13. 验证与验收

以下保留设计阶段提出的验收要求；已实现能力和实际执行的测试见 [TUI 使用指南](tui.md)，此表本身不表示所有真实环境场景都已验证。

| 场景 | 应验收的结果 |
| --- | --- |
| 空目录默认部署 | 四个目标文件按计划创建，两个基础入站和客户端节点一致；不修改防火墙 |
| 自定义 18388 / 18443 | 模型、服务端、客户端、TCP/UDP 检查和防火墙提示使用同一端口 |
| 非法/重复端口 | 下一步不可用，错误就近显示，不触发 Docker、不写文件 |
| TCP 空闲但 UDP 已占用 | SS 冲突，无法被仅 TCP 的检查漏过 |
| 无 `ss`、无进程详情权限 | 显示降级/未知和具体检查来源，不误报所有检查通过 |
| Docker daemon、Compose、目录权限失败 | 正确阻塞相关能力，显示可执行建议，程序不提权 |
| 老 Compose v1 / 远程 Docker context | 不允许因 WARN 或 socket 误判而进入部署 |
| 已有文件或外部修改 | 拒绝新部署覆盖和过期预览；给出诊断入口 |
| ISP 更新保留密码 | 草稿明确保留，不把掩码写入配置；修改为空则报错 |
| ISP 特殊字符 / IPv6 | 引号、美元、反斜线按现有序列化处理；IPv6 正确加方括号 |
| ISP 测试失败或取消 | 不写配置；结果仅描述已完成的测试层级 |
| ISP 添加/更新/移除 | 只管理 `.env` 与 `config.json`；`clash.yaml` 字节不变；保留无关路由 |
| 无变更 / 仅 env 变化 | 按真实分支展示是否写文件、是否重启、是否检查健康；取消重启不安装 config |
| ISP 重启失败，恢复旧服务也失败 | 文件恢复状态与服务状态分开显示，保留可用恢复信息 |
| 首次部署中途失败 | 保留真实完成状态与已有生成凭据，重试不重新生成密钥 |
| Ctrl+C / resize / 非 TTY / SSH 断开 | 不误提交，正常可处理信号恢复终端；未完成操作下次可见 |
| 敏感值和外部日志 | 新旧秘密、分块输出与错误均脱敏；ANSI 控制序列被过滤 |
| 发布兼容性 | 现有测试、typecheck、build、pack、bundle 和 license 检查通过 |

测试策略：纯函数覆盖校验、模型和 reducer；注入 System/Docker/文件依赖测试计划与恢复；小量 PTY 集成测试覆盖焦点、密码粘贴、resize 和中断；真实 Debian/Ubuntu VPS 验证一次 Docker 部署与端口自检。不要只做整屏快照，它无法证明没有写错文件或漏检 UDP。

## 14. 首版设计决策汇总

1. 显式 `tui` 入口，已有 CLI 继续可用。
2. 首次部署选择端口；已有部署首版只查看端口。
3. ISP 与现有两节点、独立服务端路由保持一致，凭据更新使用显式“保留/修改”。
4. 依赖检测和操作执行提供结构化事实；未知、跳过与失败分别呈现。
5. 写入前必须预览；提交后如实报告文件、服务与恢复状态。
6. 优先验证 Ink 整体打包，保留现有零外部运行时依赖约束。
